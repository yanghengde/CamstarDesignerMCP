## 1. 实施原则

本文件把产品设计转为开发和测试可核对的合同。以下模型、接口名称和状态是**拟议合同**，不是现有 API 文档。编码前应完成严格模型与样例评审，尽量复用已有执行链，不再建立第二个 WCF 执行器。

实施顺序为证据读取和状态模型 → 工作区与映射 → 页面 → 测试复现 → 增强 → 保存发布。单纯替换界面不足以完成本模块。

## 2. 拟议领域模型

### 2.1 模型清单与身份

| 模型 | 关键字段/关系 | 不变量 |
|---|---|---|
| WorkspaceContext | owner、project_id、workspace_code、source_snapshot、mode、selection、revision | 与聊天独立；临时浏览不产生历史；服务端核对项目归属与修订 |
| BusinessOperation | id、revision、业务名、说明、项目/环境范围、entry、targets、form、record_source、capabilities、evidence | 业务名不是执行身份；可用性由证据和能力推导 |
| EntryBinding | 绑定 ID、对象/字段/方法/事件、直接/继承/覆盖来源、CLF ID、源快照、附着参数 | 稳定身份来自 SDK；无完整有效值时状态明确 |
| ClfDefinitionSnapshot | CLF ID/name、workspace、source_sha256、calls、declarations、references、completeness | 函数以调用身份和原次序保留，不能按函数名合并 |
| ParameterObservation | 参数身份、层次、type/direction、value/expression、availability、source、scope | 缺失与 null 分开；库/附着/输入/运行值不互相回填 |
| BusinessRecordRef | connector、record_id、transaction_id/request_id、environment、time、object_identity | 一次交易的身份与业务对象身份分开；无交易 ID 时明确范围 |
| Inspection | id、record_ref、mapping_snapshot、evidence_refs、findings、limitations、next_actions | 查看不重放；发现分事实/推断；不覆盖原回执 |
| TestCaseRevision | id、revision、parent_run_id、mapping_revision、输入、预期、原版本和目标版本 | 保存不携带写入授权；修改形成新修订 |
| TestRun | 现有运行 ID/request_id/spec/result + 分层状态、快照与关联 | 原请求/原回执不可变；重跑生成新运行 |
| TraceEnvelope | parser_version、原来源、树节点、调用路径、参数观察、截断、匹配范围 | 原文与派生视图可追溯；未匹配节点仍可查看 |
| ChangePlanRevision | id/revision、需求来源、base_source、operations、diff、impact、preflight、cases | 修改后旧预检失效；原值和身份必须匹配 |
| DeliveryReceipt | plan_revision、阶段、目标、输入/输出哈希、结果、错误、恢复依据 | 各阶段独立，不能把部分完成覆盖为全部失败 |

首期不要求全部建表，但关系和身份不得依赖标题、中文名或聊天中的文字。所有持久化模型增加 schema_version、创建/更新时间及来源字段，升级时显式迁移。

### 2.2 参数与证据可用状态

建议统一枚举：`available`、`not_selected`、`not_collected`、`unsupported`、`failed`、`not_applicable`。截断与部分完成使用独立 completeness 信息，不折算为成功。

`availability=available,value=null` 表示确实读取到空值；`not_collected` 表示没有取得值。请求中 `未提交` 以字段是否存在或显式 presence 表示，不能转换为 null。显示为掩码的敏感值增加 `redacted` 标识，不能据此作相等断言。

每个 EvidenceRef 包括：来源类型、来源记录 ID、采集时间、版本/环境、范围、完整性、原文定位及可用状态。没有目标 CLF 名称证据时，不能仅凭业务提示相同生成触发证据。

### 2.3 业务映射状态

映射工作流：`draft → checked → active → needs_review / disabled`。`checked` 说明配置和来源经过核对；运行是否确认、附着参数是否完整、历史是否可查询、能否测试分别保留能力状态，不能用一个 active 覆盖所有缺项。

启用检查：服务/方法存在，表单字段兼容，目标记录来源可用，适用项目和环境明确。无法读取绑定参数的映射仍可用于查看已有业务回执，但必须标缺口，不能称完整入口逻辑已核实。真实测试还需要独立满足执行条件。

映射修订乐观并发更新。版本漂移产生 needs_review；历史保留原修订，不批量改写原记录。停用映射不删除历史回执。

## 3. 状态推导与现有结果兼容

### 3.1 运行状态

拟议逻辑阶段：`preparing → queued → invoking → returned`，以及 `rejected_before_invoke`、`failed_transport`、`interrupted`、`unknown_after_invoke`。名称可在实现评审后调整，但语义必须保留。

当前存储主要为 running、passed、failed、error、interrupted；不能在未改后端时仅凭前端计时推测 queued/invoking。兼容层先保留原字段，新增结构化执行阶段；只有后端产生真实阶段事件后才显示对应状态。

| 现有结果 | 新界面解释 | 禁止推导 |
|---|---|---|
| status=passed | 已配置断言通过 | 不等于目标部署版本整体通过 |
| outcome=rejected，预期=rejected | 业务拒绝，可符合异常用例预期 | 不直接显示成系统故障 |
| clf_trigger_verified=true | 本次取得目标 CLF 名称证据 | 不等于每条函数已执行或逐行匹配 |
| runtime_verified=true | 现有本次请求级验证字段 | 不等于 deployment_version_verified |
| source_current=false | 本次结果基于旧工作源 | 不抹去原回执，不自动改成新版本 |
| error/interrupted、outcome=unknown | 业务状态未知，需核对 | 不假定未写入，不自动重放 |
| primary_response 包含写入成功，后续回读错误 | 原业务返回成功，回读未完成 | 不显示“未保存” |
| output_truncated=true | 证据不完整，未覆盖内容未评估 | 不对缺失字段判通过 |

### 3.2 五个独立维度

- execution：是否到达调用、是否有完整响应；业务效果未知时有专门标识。
- business_outcome：success / rejected / unknown。
- assertion_result：passed / failed / not_evaluated / partial，并保留逐条实际值和来源。
- target_evidence：CLF 名称证据、调用级证据、运行值分别记录；未取得不必然意味着未执行。
- provenance：工作源、构建、客户端、环境及部署关系分别为 matched / mismatched / unknown。

若必须显示汇总标题，由规则表推导，并同时显示限定范围；汇总不得隐藏关键缺项。多目标规则按目标分别记录，不用任一规则有证据代表全部有证据。

### 3.3 幂等、恢复与取消

继续使用当前 `(owner, request_id, fingerprint)` 的请求去重。发送前生成 request_id 并保留；响应丢失时查询同一 ID，不生成新 ID 再执行。客户端查不到接受状态时先核对，不能视为未接受。

刷新/页面关闭不取消服务器调用。界面如有“停止等待”，文案说明只是停止前台等待。只有厂商能力证明服务器已停止且知道业务结果时，才提供真正取消；杀死客户端进程不能证明交易回滚。

当前执行锁是单进程锁。首期维持单服务实例执行约束；多进程/多机调度前要新增跨进程任务领取、租约和目标并发控制，不能以现有内存锁宣称全局只执行一次。

### 4.2 拟新增服务合同（路径待接口评审固定）

| 服务 | 最小请求/结果 | 副作用 |
|---|---|---|
| 工作区读取/选择 | workspace_id、期望修订、项目与选择；返回新上下文与失效项 | 仅有意义的选择/草稿保存，不创建聊天 |
| 业务操作目录与修订 | 名称、范围、entry/form/source、来源和预期修订 | 保存映射配置，不调用交易 |
| 入口有效参数读取 | 源快照、绑定身份；返回四层中的定义/附着层及来源 | 只读，前后检查源不变 |
| 检查记录查询 | connector、映射修订、分页游标和业务条件 | 首期只读本工具回执，后续逐个接入来源 |
| 检查结果读取 | record_ref、mapping_snapshot；返回 findings/evidence/limitations | 不重放交易；可持久化检查事实 |
| 排查包准备 | 当前检查/运行、用户说明、选择的证据 | 本地生成或导出，默认不向外发送 |
| 运行复制为用例 | 原运行 ID、目标版本意图；返回草稿与需核对项 | 不执行，清除原写入授权 |
| 轨迹读取/关联 | 运行 ID、解析器版本、定义快照 | 只产生派生视图，保留原文 |
| 运行/方案差异 | 两个有归属的快照 ID | 只读，明确输入及环境差异 |
| 后续保存/交付 | 方案修订、来源前提、明确目标、阶段身份 | 独立权限和独立回执，G4 前不启用 |

共同要求：严格输入模型、服务端归属和目标校验、可定位错误码、schema_version、局部完整性与 capability 信息。前端不能提交“已通过”“已部署”并让后端当作证据保存。凭据不进入 URL、草稿、模型上下文或导出文件。

只读请求可做有限重试；写入接口超时不得自动以新幂等 ID 重试。HTTP 4xx/5xx 不等价于业务拒绝，业务拒绝须有明确业务响应。

## 5. 存储、缓存和审计设计

- 复用测试数据库和现有项目来源；新增记录使用明确 kind 或独立表，先核对归属、索引和修订合同。不要用聊天标题当外键。
- WorkspaceContext、映射、草稿与真实运行分开保存。原运行 spec/result 作为证据冻结，用户备注以附加记录存储。
- 持久化 schema 迁移须有版本号、迁移前备份和失败恢复；旧回执缺字段标为 unknown，不补造历史值。
- 缓存键包含源哈希、SDK/桥实现版本、工作区及绑定身份。运行派生视图还包括原运行和解析器版本。不能在新源上返回旧入口参数。
- 不重复保存大型轨迹到每个模型；用受控 EvidenceRef 引用。原文存储位置不得由浏览器传任意文件路径决定。
- 原始回执尽可能完整；如采集阶段已截断，导出亦标明截断。UI 折叠不等于采集截断，二者分别记录。
- 首期沿用现有凭据保护和脱敏；后续共享/外发前增加可评审导出内容及实际访问权限。
- 变更实施后记录操作者、原值/新值、来源、预检和交付阶段；查看行为可轻量统计，不为每次点击创建业务历史。
- 数据保留期限、运行证据归档与删除策略在多用户/长期部署前明确；不得删除仍被发布验收或排查包引用的证据而不提示。

### 7.5 示例规则的语义验收

以已读取的 `ES_ValidateProduct` 库定义为样例，针对严格小于结束时间、严格大于开始时间的表达式准备：交易早于开始、等于开始、区间内、等于结束、晚于结束、边界缺失以及产品上下文缺失。

语义预期依据真实表达式和类型确认：严格比较下“相等”不触发对应分支；没有某个日期值时不能随意新增限制。产品上下文缺失时只能说明本段条件未进入，不能推定整笔交易允许。时间按实际 UTC/时区语义，不能用显示字符串比较。测试前必须核对所选入口附着表达式是否与库定义相同。

以上先作静态解释与表单样本；只有真实运行且取得足够证据后，才记录运行验证结果。

## 9. 每阶段交付包与阻止放行的问题

每阶段至少包含：实现范围和未完成项、模型/API 版本、迁移及兼容说明、真实或隔离验证证据、适用厂商版本、自动化与界面验收结果、性能基线、恢复说明。

自动化优先覆盖状态推导、来源失效、归属、幂等、类型、绑定身份和部分失败；SDK 合同使用实际组件的隔离样本；页面使用真实契约和隔离回执验证。真实业务写入须在明确测试目标上执行，不以开发演示数据宣称生产可用。

阻止放行：

- 重复交易、跨上下文数据混用、原历史被覆盖、凭据泄露。
- 将证据缺失、通信错误或截断判为规则/部署通过。
- 库默认值冒充附着值、定义顺序冒充实际轨迹、推断的路径冒充完整调用链。
- 保存或发布部分失败后失去已完成事实与恢复依据。
- 以页面模式代替服务端权限，或借新 UI 扩大 CLF 助手写入能力。
