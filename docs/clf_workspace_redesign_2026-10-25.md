# CLF 查看、操作与调试设计建议（2026-10-25）

> 本文保留为交互探索与市场参考。后续实现以 [CLF 核心模块产品设计](clf_core_product_design.md) 和 [数据合同、实施任务与验收](clf_core_delivery_and_acceptance.md) 为设计基线；本文原型不是已实现能力说明。

本文是设计方案，未修改现有产品页面、MDB 或测试环境。附有可交互的界面草案，草案中的运行结果均为示例。

## 设计结论

把 CLF 做成一个稳定的工作区：**找到入口 → 看懂有效逻辑 → 复现问题 → 核对修改**。主内容是当前规则及所选业务入口，助手在需要解释、规划或排查时展开。

结合操作人员的使用要求与下文市场产品调研，默认入口调整为“业务检查”，以业务操作和业务记录开始；“工程排查”展开规则工作台。“故障排查向导”保留为工程任务入口。它们共享同一上下文和底层数据，不再是互不相干的页面。

## 比上一轮简化更重要的改动

上一轮已增加对象筛选、规则卡片、折叠详情、方案差异和验证链接。继续增加折叠区，难以解决以下问题：

| 问题 | 本轮设计处理 |
|---|---|
| 主屏是聊天，规则与参数挤在窄栏 | 规则占主区域；助手改为侧边按需展开 |
| 相同 CLF 在不同入口可能有不同参数 | 将“CLF 库定义”和“入口有效定义”明确区分 |
| 技术名称和业务说明之间来回找 | 保留 CLF 真名作为稳定标识；中文说明、类别和入口作为辅助信息 |
| 函数参数、CLF 声明、业务输入、运行值混在一起 | 分层呈现，参数来源与可用状态始终明确 |
| 点击验证后又要重新选择服务、方法和版本 | 在同一规则页切换验证，继承上下文；歧义仅确认一次 |
| 业务返回成功就容易被理解为规则通过 | 分开显示业务返回、目标 CLF 触发证据、输入预期是否满足和版本核对情况 |

## 页面结构

沿用产品全局导航，将 CLF 主入口命名为“CLF 工作区”。原“CLF 逻辑测试”先作为别名跳转到工作区的“验证”视图，保留旧链接中的对话、项目、规则及版本参数。WCF 接口测试保持独立，服务于通用接口调试。

工作区顶部只保留：项目、当前工作区、CLF 真名、所选入口/库定义，以及“询问助手”。路径和完整哈希位于来源详情；没有项目或无法唯一决定入口时再要求选择。

左侧目录提供三个分组：最近查看、当前对象相关、全部 CLF。搜索支持真实名称、已保存说明和已核实标签。默认不铺开几千条目录。系统/客户、直接/继承关联、类别使用简短来源标识；名称相似不当作绑定证据。业务说明若由 AI 推断，标记为“说明草稿”，不覆盖厂商元数据描述。

右侧主内容只有三个任务页签：

### 查看逻辑

- 首屏显示一段简短作用说明和未决入口问题。
- 默认使用有缩进、可折叠的函数列表；条件、处理、调用子 CLF、异常退出可快速辨认。保留执行次序、禁用状态和真实表达式。
- 只有能可靠识别的结构才分组；复杂控制流保持原始顺序，不擅自转换成简化流程图或推定跳转。
- 选择函数后，旁边显示参数表：参数名、方向/类型、当前表达式、值的来源。重复函数以真实 call ID 区分。
- 提供“只看业务说明 / 原始表达式”切换；原始函数名在说明视图仍可查看。
- 子 CLF 与 callsuper 支持按需展开；未展开、循环引用和读取失败有明确状态。
- 单独提供“在哪里使用”抽屉，显示已声明引用的对象、方法/事件和字段，支持反向进入指定入口。动态调用覆盖范围仍单独说明。

### 验证与排查

普通操作收敛为：**选择实际入口 → 选择或填写业务输入 → 配置预期 → 运行 → 查看差异**。

- 从当前规则自动继承项目、工作区和来源版本。环境和客户端沿用已保存配置，并在顶部可确认。
- 只有引用与真实契约能唯一匹配时才带入入口；有多个候选时列出简短选项；只有抽象基类/自定义方法时显示“实际业务入口待选择”，不默认使用 ProductMaint。
- 输入表单根据真实契约生成。优先名称、版本、容器等业务输入；明确区分未提交、null、空串、0、false，不能把空白统一当作不传或清空。
- “正常 / 异常 / 边界”是用例分组。建议用例先为未执行，预期可以人工调整。用户可从历史记录复制输入，编辑后重跑，保留父记录关系。
- 开始前用一句话显示操作和目标记录。会写入业务数据的方法要求本次明确授权；界面不标成“无副作用模拟”。断开连接继续按现有后台任务机制保存结果，不自动再次提交。
- 结果首屏显示预期与实际差异、错误提示和目标 CLF 是否取得明确触发证据。原始报文和完整服务轨迹放入详情。
- 没有轨迹时保留业务结果，并说明“未取得目标 CLF 触发证据”；不能把 CLF 定义列表当作执行轨迹。
- 轨迹能提供参数解析值时，展示“表达式 / 实际值 / 来源”。没有值就显示“本次未采集”，不在浏览器计算一个替代值。
- 先显示首个可定位的异常及其调用链，再允许展开整棵轨迹。只有实际标识与来源足够确定时才与定义中的调用行关联；无法确定时保持轨迹独立，并说明匹配范围。

### 修改方案

- 用户可以从选定参数发起“准备修改”，也可以用自然语言说明业务要求。
- 差异按“位置、原值、拟定值、影响入口”组织。修改目标必须写明：库默认值、特定入口参数、客户覆盖或客户副本。范围不能被几个通用规则模板隐藏。
- 系统/共享规则优先明确客户扩展位置，不自动改写所有使用者。
- 现阶段主按钮为“检查方案”，结果为官方内存预演与冲突。后续实施要接入现有设计保存、编译、发布及回读流程，再启用对应动作。
- 模板只覆盖能映射到真实函数与参数的常见规则。复杂规则保留表达式与逐步差异，不强行转换成几项条件开关。

## 参数来源：排查必须回答的问题

参数详情分开显示四层信息：

| 层次 | 用户看到什么 | 缺失时的显示 |
|---|---|---|
| CLF/函数库定义 | 声明、类型、方向、默认表达式 | 未读取 |
| 所选入口 | 该 CDO/字段事件或方法附着后的实际配置；直接/继承/客户覆盖来源 | 尚未选择入口，或当前接口尚未取得该值 |
| 本次业务输入 | 实际提交和回读的相关输入 | 未提交/未回读；与空值分开 |
| 实际运行 | 服务器回执中解析出的参数值和轨迹 | 本次未采集；不假设与表达式值相等 |

“查看库定义”随时可用；只有取得绑定实例参数之后，才能称为“入口有效定义”。当前 `get_clf` 返回库调用和引用，桥的通用反射并未完整展开附着后的所有函数参数，这部分需要补充读取合同与实际 SDK 验证，是第一阶段的后端重点。

还要区分当前工作 MDB、用于生成客户端的版本及服务器实际部署版本。已有记录明确尚不能自动证实全部版本关系；界面将相应状态显示为待核对，不把版本号存在当作已一致。

## 调试能力分期

| 阶段 | 可提供的用户能力 | 依赖与限制 |
|---|---|---|
| 首期 | 固定入口、类型化输入、历史复现、用例分组、预期/实际对比、异常定位、轨迹查看 | 复用现有 WCF 真实调用和回执；先改善表单与结果组织 |
| 随后 | 函数调用与轨迹关联、参数表达式/实值对照、两次运行差异 | 先核实实际服务器轨迹字段、调用标识、时间及版本来源；有值才显示 |
| 另行验证 | 断点、单步、暂停/继续、监视变量、执行时修改值 | 需要厂商运行时调试会话和可控上下文；当前代码只有请求跟踪与返回轨迹，尚不能支持这些操作 |

“离线试填输入”可以检查表单与类型，但在没有官方独立表达式执行合同前，不提供伪装成真实调试的浏览器解释器。服务器日志的采集、权限和脱敏可以后续接入，首次交付无需要求用户每次手动启动全局高等级跟踪。

## 响应速度与说明复用

- 打开规则、选函数、查看表达式和参数来源使用确定性的元数据读取，不等待模型回答。
- AI 解释由明确动作触发，围绕当前 CLF/入口/选中函数；初次可以只显示厂商说明与定义，中文解释稍后补齐。
- 解释结果按项目、工作区、CLF、所选绑定、MDB 哈希及解释规则版本关联；来源或入口改变后失效，避免把库定义的解释沿用为另一个入口的有效值说明。
- 聚合直接函数、参数、标签和引用，复用本轮已经实现的只读批量查询与进程缓存；不为四千多条目录预先逐条调用模型。
- 调试输入和实际运行走现有确定性服务调用，不通过模型多轮循环才能执行。完成后用户可以对当前回执发起“解释这次异常”。

## 交互状态与上下文

同一工作区维护一个明确的选择：项目、工作区、CLF、绑定入口、工作 MDB 版本。验证再关联环境、客户端版本、用例和运行记录。页签切换保持选择与草稿，不切换到另一个默认项目。

- 入口未定：允许看库定义，阻止把它标为有效绑定参数；验证页给出入口选择动作。
- 切换 CLF：保留项目及环境，清空不兼容的入口和测试结果，询问或保留未提交方案草稿。
- 来源改变：保留旧记录以供对比，当前结果标为旧版本；重新核对后才能提交新方案/请求。
- 轨迹不可用：显示业务结果，不填造逐步状态或变量值。
- 调用中断/超时：沿用现有“结果未知”的真实状态，显示核对与查记录操作，不自动重试可能写入的请求。

## 首批交付建议

1. 调整布局与路由：规则为主、助手按需展开，查看/验证/方案共享上下文，保留旧入口兼容。
2. 补充绑定实例参数读取和来源对照，解决“库默认值改了但实际没生效”的排查基础。
3. 简化验证表单与结果，支持复制历史输入，异常与真实轨迹优先展示。
4. 再做函数轨迹关联和运行对比，最后评估独立的断点调试接入。

验收以任务为准：能够从已知 CLF 进入函数/参数；能够从业务对象进入真实绑定；能够明确看到参数来源差异；能够使用同一输入复现一次问题并分辨业务返回与目标 CLF 证据；普通路径无需手填 JSON；复杂路径仍能取得完整表达式、参数、原始回执和来源。

第一份原型演示“规则工作台”和“故障排查向导”两种组织方式；本轮另补充“业务检查 / 工程排查”的共享上下文交互。示例数据不代表已找到实际业务入口、已取得运行值或真实业务验证通过。

## 市场参考与本项目的取舍（2026-10-25）

本轮查阅了以下产品的官方文档。它们分别提供流程运行检查、实例运维、低代码调试和历史执行复现能力，是交互参考，不代表与 Camstar CLF 的运行时或模型兼容。以下落地方案是根据本项目约束作出的设计判断。

| 参考产品 | 官方设计方式 | 在 CLF 中采用的方式 | 适用范围 |
|---|---|---|---|
| [Microsoft Power Automate](https://learn.microsoft.com/en-us/power-automate/see-a-flow-run) | 每个步骤显示状态与耗时，展开查看输入和输出 | 结果先行，异常步骤优先，技术详情按需展开；运行耗时有来源时才显示 | 操作人员看结果，工程师展开具体证据 |
| [Camunda Operate](https://docs.camunda.io/docs/8.9/components/operate/userguide/basic-operate-navigation/) | 围绕一次流程实例组织版本、状态、流程进度以及 Details / Incidents / Variables | 围绕“一次业务操作”组织输入、回执、异常、规则与版本；点击步骤后联动详情 | 排查一次实际失败，避免从几千条 CLF 中猜测 |
| [Mendix Studio Pro](https://docs.mendix.com/refguide/debug-microflows-and-nanoflows/) | 调试流程与变量值并行显示，支持运行时断点与单步 | 工程视图并排查看函数、参数和已有运行值，减少切换 | 只借鉴布局；当前 CLF 接口没有断点会话，不能照搬暂停/单步按钮 |
| [n8n](https://docs.n8n.io/build/understand-workflows/understand-executions/debug-executions.md) | 将过去执行的数据复制到编辑器，使用原输入排查 | “复制为测试用例”带入输入、来源、原回执和版本；编辑后再明确发起验证 | 复制历史输入是准备动作，不自动重放可能写入的交易 |
| [Camunda DMN](https://docs.camunda.io/docs/components/modeler/dmn/decision-table/) | 用输入、输出和规则构成决策表 | 对简单且能完整映射的判断展示“条件 → 结果”业务摘要，并能回到原表达式 | 作为只读摘要；复杂顺序调用、副作用、继承与调用链继续保留函数视图 |

### 推荐组合

采用 Power Automate 的逐步结果、Camunda 的单次实例排查、Mendix 的函数/变量并排查看和 n8n 的历史输入复现。优先学习任务组织与信息层次，不在首期引入通用流程编辑器或更换规则引擎。

操作人员默认只走三个动作：**选择业务操作 → 选择业务记录 → 查看检查结果**。例如“产品有效期检查”，不要求用户知道 `ES_ValidateProduct`、CDO、字段事件或 WCF 服务名。业务名称到真实入口的映射由工程师建立，保存来源与核对状态；存在多个入口时明确选择，不根据名称相似自动确认。

默认检查读取已有业务回执、可用轨迹和相关数据，不重新执行业务交易。没有历史回执时可以给出静态检查，但必须显示“当前资料检查”，不能显示成“该 CLF 已执行”。需要真实执行的测试在工程视图中准备，明确目标环境、实际入口与写入影响，复用现有调用与授权合同。

检查结果遵循“结论、依据、下一步”：

- 已有明确回执：显示实际业务返回、可定位异常和来源；业务拒绝可能符合异常用例预期，不直接称为测试失败。
- 只有静态数据：显示“发现可能问题”，区分当前数据与交易发生时的数据，不能据此认定历史失败根因。
- 证据不足或执行状态未知：显示未确定部分和核对动作，不用绿色成功掩盖目标 CLF 触发证据的缺失。
- 下一步只提供与证据相符的动作，例如核对产品版本/日期、补充回执、复制为测试用例。操作人员可“准备工程排查信息”，不会在未授权时自动向外部人员发消息。

工程师切换“工程排查”时保留同一业务记录和回执，继续查看真实入口、CLF、定义次序、实际轨迹、参数四层来源、版本差异和测试准备。真实函数名是稳定标识，业务名称用于辅助理解。只有证据允许时才把轨迹关联到具体函数调用；定义中有七个函数不等于本次执行了七步。

### 首期页面与验收
