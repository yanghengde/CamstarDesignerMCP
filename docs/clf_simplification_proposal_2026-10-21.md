# CLF 工作区简化方案

本方案依据当前 `/clf`、`/clf-test` 实际页面和对应代码整理。此次为产品与流程评估，尚未修改运行中的 CLF 功能。

## 当前使用负担

1. 当前工作 MDB 有 4,289 个 CLF，页面默认列出前 50 个技术名称。使用者通常知道业务对象和要做的校验，却不知道应搜索哪个 CLF。
2. 设计入口同时展示对话、项目路径、CLF 目录、函数顺序、调用 ID、参数、声明参数和引用。说明结果又在聊天中重复展开，业务结论很难从技术细节中找出来。
3. 进入测试页后，还需选择项目、客户端产物、服务和方法，填写字段路径、返回路径、断言及回读 JSON。设计中已经确定的信息没有充分沿用。
4. 当前 CLF 设计助手仅支持读取和官方内存预演。`metadata_preflight_passed` 不代表已经保存、发布或在实际业务中运行。

## 建议主流程

```text
选择业务对象 → 查看或描述规则 → 审核差异 → 验证规则
```

前台以“业务规则”为中心，CLF 名称、函数和事件作为底层实现信息。页面保留一个主工作区，用“规则设计 / 规则验证”切换当前任务，沿用同一项目、规则和来源版本。

## 默认页面

| 区域 | 默认展示 | 按需展开 |
|---|---|---|
| 当前上下文 | 当前设计项目、业务对象 | MDB 路径、来源哈希、工作区和客户端版本 |
| 规则目录 | 最近查看、当前对象相关、客户自定义规则 | 所有 CLF 的技术检索和分页 |
| 规则内容 | 中文业务摘要、触发入口、条件、处理动作和提示 | 全部真实函数顺序、调用 ID、参数及引用 |
| 修改审核 | 改前 / 改后、影响哪些对象、尚需确定的问题 | 完整操作参数、预演前后定义 |
| 验证结果 | 预期行为、实际行为、目标规则是否触发 | WCF 报文、断言 JSON、服务器轨迹 |

当前项目优先沿用对话或设计进度的选择；没有明确选择时才使用唯一项目或已绑定的系统默认项目。有多个合理候选时保留一次明确选择，不静默切换项目。

系统环境与业务账号沿用 WCF 页已有的默认连接机制，凭据只在后端使用。项目或来源变化时，旧方案和测试输入需要重新核对。

## 规则编辑

常用模板先支持：必填、长度限制、数值范围、允许值、条件拦截。复杂业务继续允许自然语言描述。

使用者主要填写四类信息：

- **何时执行**：实际绑定的业务入口；展示容易理解的名称，保留真实事件映射。
- **检查什么**：业务字段、比较方式和条件值。
- **如何处理**：允许继续、阻止操作或采用已有的业务处理。
- **提示什么**：预期的错误提示或已有标签。

助手读取真实函数库和原有绑定，将需求转换为候选变更，进行官方内存预检。不能把任意表达式或复杂 CLF 强行转换为几个简单条件；无法可靠还原时显示“复杂逻辑”，保留业务说明与高级详情。

系统或共享 CLF 的修改需要先确认引用范围和客户扩展方式。普通界面审核业务差异，高级详情仍保留完整原值、调用身份和执行顺序。

## 说明与状态

普通说明默认只展示：

1. 当前规则做什么。
2. 本次准备修改什么。
3. 还需确定哪一项业务信息。

读取函数库、核对引用等过程汇总为一条进度状态；技术证据集中在详情中。历史解释可按 MDB 哈希与 CLF 来源复用，来源变化后重新读取。

页面状态按实际证据显示：**方案草稿、方案检查通过、已保存、已发布、业务验证通过**。未完成的阶段不提前显示成功。

## 测试衔接

从当前规则进入验证时，自动沿用项目、规则、环境和客户端，并根据已核实的绑定推荐真实服务入口。入口未知或有多个候选时显示待确认事项，不自行推定。

优先提供正常、违反规则、空值 / 边界三类用例建议。页面展示必要业务输入和预期提示，报文与断言由系统组织；建议用例初始状态均为“未执行”。

CLF 需要在相应业务上下文中验证，不能将任意 CLF 当作独立表达式直接执行。实际调用如涉及业务写入，应明确展示涉及的记录和操作。服务返回符合预期、取得目标 CLF 的触发证据分别记录；没有目标规则触发证据时显示“规则触发未确认”。

## 当前规则的展示例子

以现有 `ES_ValidateProduct` 为例，可以将首页摘要收敛为：

> **产品有效期校验**
>
> 检查内容：产品开始日期不能晚于交易时间，结束日期不能早于交易时间。
>
> 违反条件：使用现有的“产品不在有效期”错误提示。
>
> 待确认：该逻辑通过自定义方法关联，实际业务调用入口与参数来源仍需核实。

原有七个函数调用、参数表达式、标签和引用完整保存在“技术详情”中。这个摘要描述已有定义，不代表已经确认每笔交易都会触发该规则。

## 实施顺序

第一步先完成默认上下文、业务摘要、规则卡片、技术详情折叠，以及设计到验证的信息带入；可保留现有底层读取与预检能力。

第二步加入已验证的常用规则模板与改前 / 改后差异，减少对自然语言长对话和手填表达式的依赖。

第三步把方案交接到现有设计保存、编译和发布流程，并完善实际业务验证。当前 CLF 模式的工具权限明确禁止写入，保存按钮应在完整交接和回执能力接通后启用。
