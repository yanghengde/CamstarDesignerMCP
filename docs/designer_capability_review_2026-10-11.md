# Designer 能力 Review · 2026-10-11

以下为修复前的审查记录。后续实现与验证结果见 [能力修复说明](designer_capability_fixes_2026-10-11.md)。

## 结论

当前程序具备新建对象、指定继承、添加字段、简单属性更新、字段类型更换、部分 CLF/查询/映射设计，以及受限删除入口。主要不足集中在已有设计的关系调整、Designer 手工修改后的接续设计、删除与复杂更新的验收。

“有操作入口”与“保存、导出、交接、发布、验收全部可用”需要分别判断。不能将现有通用工具理解为完整的 Designer 编辑器。

本次完成代码审查、现有测试和隔离 MDB 实验；未修改业务代码、项目工作 MDB、服务器 MDB 或数据库。文件合并和多人兼容继续由 Opcenter 处理。

## 能力清单

| 能力 | 当前状态 | 现有范围与缺口 |
|---|---|---|
| 新建 CDO、指定父对象 | 已实现 | `create_cdo`，可选择创建表、Revision Base、Maintenance。已有对象重新选择父对象没有专用操作。 |
| 新建字段、字段类型、字符串长度 | 已实现 | 支持持久化与列表参数；专用 CDO 工具默认持久化，通用 `add_field` 默认非持久化。 |
| 修改说明、标签文本、可见性等属性 | 已实现 | `patch` 仅开放实际 schema 中允许编辑的简单属性，并检查每个属性的原值。不是所有关系都能通过属性修改。 |
| 重命名 | 有缺陷 | 可编辑名称，但保存后仍按旧名称定位，导致成功保存的测试副本被报告为失败。 |
| 更换字段类型 | 已实现，验收有限 | `change_field_type` 调用厂商方法并检查原类型；未覆盖所有类型转换的数据兼容性、业务接口行为。 |
| 修改已有对象的父类 | 缺失 | `ParentCDOName` 只读，`ParentCDO` 为被禁止编辑的对象引用，`ParentCDOID` 为受保护 ID。自然语言无法通过现有动作完成这项修改。 |
| 继承字段覆盖 | 部分实现 | 属性更新会在目标 CDO 建立覆盖，避免直接修改父对象字段；没有撤销覆盖、恢复父级定义的专用操作。 |
| 目录、存储分类、工作区调整 | 部分实现 / 未验收 | `StorageCategoryName` 标记为可编辑；缺少经过验收的目录移动、工作区迁移及相关关系调整流程。不能一概说目录完全不能修改。 |
| 删除 | 受限实现，闭环不完整 | 仅当前客户工作区拥有且厂商 `IsInUse()` 判定未使用的定义。系统定义、下层工作区定义及引用清理不在通用删除范围内。隔离实验确认未引用字段类型可删除；删除后的导出与发布验收仍有缺口。 |
| CLF | 部分实现 | 新建、复制、增加调用、调用排序、调用参数表达式修改已接入；调用替换/删除、CLF 自身参数维护缺少专用操作与完整验收。通用 `patch/delete` 对部分子定义可能适用，不等同于所有场景已支持。 |
| 事件绑定 | 部分实现 | 能创建 CDO/字段事件绑定；`bind_event` 明确拒绝已有绑定。已有绑定替换、解绑没有专用操作或验收流程。 |
| 查询 | 部分实现 | 新建、添加数据库方言、修改查询文本；创建/添加文本会同步参数，通用文本 `patch` 没有显式重新同步参数。参数生命周期与运行执行缺少完整验收。 |
| 对象映射、字段映射 | 部分实现 | 可创建映射、增加字段映射；字段映射未列入可查询/修改的 `kind`，缺少字段映射更新、移除的专用入口。 |
| 列、索引 | 部分实现 | 能添加列、创建索引、修改可编辑简单属性；已有索引列集合调整等关系操作不完整，删除/类型变更后的物理结构验收覆盖有限。 |
| 引用影响分析 | 部分实现 | 调用厂商 `GetWhereUsed(bool)`；当前组件的 `CDOField` 没有该方法，字段级影响分析不能依赖这个入口完成。 |
| 固定工作 MDB、发布后保留 10 份备份 | 已实现，接续能力欠缺 | 固定路径与保留数量已有实现；备份可查看/下载，没有恢复到当前工作 MDB 的专用流程。现有 SQL 数据库恢复是另一种能力。 |
| Designer 手工修改后继续对话设计 | 不完整 | “同步文件”只读取服务器哈希，未读回 MDB 或重建设计基线；后续交接存在覆盖手工修改的路径。 |
| 发布、服务与验收 | 部分实现 | 官方 Compile、Update Database、部分数据库检查和 WCF 生成已接入；WCF 部署为手工确认，REST、完整服务行为以及原生 XML Import 往返未形成已验收闭环。测试环境继续按配置允许不备份数据库。 |

## 优先修复的问题

### P1：服务器工作 MDB 可能覆盖 Designer 中保存的改动

触发场景：先将固定工作文件交接给 Designer，用户在 Designer 中修改并保存，然后再次通过对话生成设计。`vendor.design` 从本地工作文件生成，成功后自动调用 `review.prepare`。交接脚本只验证待上传文件的哈希，随后直接替换服务器 `InSite.mdb`，没有检查服务器文件是否相对上次交接发生变化。

这与多人合并不是同一项功能：程序至少需要检测并接收用户选定的最新文件，或者在检测到外部保存时停止覆盖。无需自行实现 Opcenter 合并算法。

定位：

- `designer/vendor.py:220`：后续设计自动刷新已交接的服务器路径。
- `designer/review_transfer.ps1:27`：直接替换服务器文件。
- `designer/review_sync.ps1:7`：只读哈希，无 MDB 回读。
- `designer/progress.py:307`：发现变化后提示“先同步”，但现有同步仍仅检测哈希，缺少恢复接续的入口。

证据：代码路径确认；未在用户服务器上执行覆盖实验。

### P1：重命名后按旧名称回读，整个设计操作报错

隔离实验将 `AssetTrace_6381` 改为随机测试名称。厂商组件成功保存，随后桥接层仍用原操作的 `name` 回读，报 `Definition missing or ambiguous (matches=0)`。重新读取测试副本的新名称能够找到对象。

外层设计函数因此判定 apply 失败，无法提交到固定工作 MDB。应使用稳定身份或最终名称回读，并处理同批次对已重命名对象的后续操作。

定位：`designer/VendorBridge.cs:354`、`designer/VendorBridge.cs:360`，外层失败处理在 `designer/vendor.py:186`。

证据：安装的真实厂商组件、隔离副本复现；源文件哈希不变。

### P2：删除缺少完整导出与验收保障

底层删除可以执行。隔离实验创建一个未引用客户字段类型后删除，重新加载列表中已无此类型。但桥接层回读核验明确跳过 `delete`；XML 校验器允许 `Create/Import/Rename`，拒绝 `Delete`；数据库验收也跳过对象、字段、列的删除节点。

本次未引用类型实验的官方差异导出为空，没有复现所有删除场景都会报 XML 错误。因此结论是删除的合同和验收不完整，不能据此宣称所有删除都不可执行。应补充实际删除对象/字段/映射场景的官方导出检查、删除后不存在断言及对应发布验收。

定位：`designer/VendorBridge.cs:214`、`designer/VendorBridge.cs:360`、`designer/metadata.py:116`、`designer/publication.py:290`。

### P2：仅修改旧对象时，进度页丢失对象和字段统计

进度页只从 `create_cdo/add_field` 推导 `package.objects`，覆盖了交接摘要原本可以识别的 CDO 属性更新对象。独立的字段类型更换、属性更新或删除会显示 0 个对象、0 个新增字段；变更明细也只显示新增字段。

页面自动生成 WCF 要求验收对象属于这个集合，集合为空时连显式指定正确对象也被拒绝。手工确认或跳过 WCF 仍可使用，不能称所有进度流程都会被阻塞。

定位：`designer/progress.py:167`、`designer/progress.py:277`、`designer/progress_actions.py:163`。

证据：静态路径确认；空对象集合分别使用默认和显式对象调用 WCF 参数检查，均被拒绝。

### P2：复杂更新与删除无法获得完整自动验收

数据库检查主要核对 CDO 父对象、字段类型/持久化状态和部分物理列；CLF、事件、查询、映射、索引的变更没有对应的完整结果检查。进度页仅将 `create_cdo/add_field/create_field_type` 归为完整验收动作，其它操作即使局部检查通过也只能得到部分验收。纯删除或纯 CLF 变更还可能因没有可执行检查而返回验收失败。

应按动作定义实际验收项，而不是统一依赖“新增 CDO 与字段”的验收流程。服务运行行为需要在部署后单独验证。

定位：`designer/publication.py:281`、`designer/publication.py:332`、`designer/progress.py:340`。

### P2：批量更新/删除没有进入现有操作数量统计

现有数量控制依据工具名的 `create_/update_/patch_/delete_` 前缀计数，且只识别 `items/records/entities` 形式的批量参数。真实入口 `generate_designer_design_package` 的变更在 `operations` 中，因此内部 `patch/delete` 被计为 0。Excel 预览确认是另一条路径，不能覆盖没有 Excel 的普通对话。

应直接按操作内容计算数量，使现有配置与真实行为一致；这不意味着新增额外的确认要求。

定位：`agent/safety.py:49`、`agent/safety.py:70`、`agent/safety.py:85`。

证据：构造含 50 个删除动作的通用设计调用，实际统计为新增 0、更新 0、删除 0。

## 新能力建议顺序

1. 先修复服务器文件接续、重命名、删除验收、旧对象变更统计，稳定已有入口。
2. 增加已有 CDO 更换父对象的专用操作：检查继承循环、同名继承字段、对象类别与存储关系，使用厂商支持的方法，并核对保存、编译、导出结果。
3. 补事件重绑/解绑、CLF 调用替换/移除、字段映射修改/删除、撤销继承覆盖、查询参数同步等专用关系操作。
4. 补存储分类/目录与工作区调整的真实往返验收；已有简单名称属性不应直接当作完整迁移能力。
5. 增加从指定 MDB 备份恢复当前工作文件的入口，并重建哈希与设计基线。MDB 恢复不能被描述成数据库也已回退。
6. 根据实际使用范围补服务部署后的接口验收。多人合并与冲突兼容仍交给 Opcenter。

## 验证记录与限制

- 全量现有测试：**162 passed, 4 skipped**，耗时 21.30 秒。
- 使用真实安装组件的隔离实验：重命名已保存但回读失败；未引用客户字段类型删除成功；CDO 父对象相关属性不可编辑，存储分类名称可编辑。
- 源 MDB 哈希保持不变；未写入工作项目、服务器文件或 SQL 数据库。
- 补充直接检查：删除 XML 标记被当前校验器拒绝；通用批量删除计数为 0；空设计对象集合不能通过页面 WCF 对象选择检查。
- 当前测试未覆盖这些完整的重命名、删除导出、关系迁移与手工保存后接续场景，测试通过不能替代这些能力的真实验收。
- `docs/designer_capabilities.md` 仍有以发布基线起步等旧描述，需要与现有固定工作 MDB 逻辑同步。
