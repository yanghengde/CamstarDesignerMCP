# CLF 专业工作区：第一阶段

## 已实现

- `/clf` 独立入口和专用对话，`/clf/records` 查看全部 CLF 历史记录。会话持久化 `mode=clf`，旧会话默认 Designer；历史列表按模式分开，仍使用同一存储和工作 MDB。
- 右侧检索 CLF、展示真实函数调用顺序/调用 ID、调用参数、CLF 声明参数、官方引用范围及来源版本。相同函数的多次调用不会合并。界面支持历史恢复和会话切换，不把前一对话的方案留在新对话中。
- 自然语言解释、影响分析与方案规划复用既有 LangGraph、模型配置和 MCP。当前模式的工具列表仅暴露只读能力；策略节点及执行节点再次检查持久化模式和选定项目，不能靠伪造工具调用、旧确认或其他文件路径执行写入。
- CLF 预检的十种动作使用按 action 区分的严格参数模型，包括必要原值和实际调用 ID；未知键、错误类型以及伪造的测试通过状态在公共工具入口被拒绝。
- 官方预检在隔离副本的内存模型应用完整操作，回传修改前/预演后的 CLF，不调用 SaveAll。新建/复制后的后续操作可在同一批次预演；读取修改前对象时不会把尚未创建的 CLF 当作已有定义。
- SSE、持久化工具回执和历史消息保留结构化 CLF 结果，页面可在流结束或返回页面后恢复。
- Excel 识别明确的规则列，保留完整规则、原始单元格、隐藏表状态和对象/字段信息；不猜测空白归属，不把空白当删除。附件卡片可带入专用对话，重复带入复用目标会话；读取时校验原附件所有权与源文件哈希。
- 字段设计预览单列业务规则待分析状态，字段生成不能当作业务规则已经实现。

## 第一阶段边界

专用页面不保存 MDB、不编译、不执行 Update Database、不生成或部署 WCF。`metadata_preflight_passed` 只代表官方内存模型接受方案，表达式语义和真实业务运行仍未验证；所有测试建议标为 `not_run`。CLF 声明参数的完整新增/类型/方向生命周期、联合变更实施和运行验收留在后续阶段。

解释结果需要区分元数据原文、局部逻辑推断与完整交易行为。父级调用、其他 CLF 调用、函数默认值和动态引用未经检查时，不据此声称整个交易必定通过。官方引用结果截断或不可用时保留范围与错误。

## 同步修复的只读进程问题

真实模型试跑发现：复用的 SDK 图会在 `GetWorkspaces()` 等方法中重新打开首次加载的 MDB，而原来的逐次调用清理已删除该文件。

只读进程现在持有一个 `resident.mdb`，与该进程/版本保持相同寿命，逐次调用的 `read.mdb` 仍及时释放。版本切换、退出或异常时清理常驻副本；调用前后检查其哈希，拒绝来源变化及意外写入。进程不能取得原工作文件的清理所有权。

## 验证

- 本机官方组件：`AddSPCAnnotation_ValidateSpecific` 读取到 5 个调用和实际引用入口；公共 CLF MCP 预检复制后仍有 5 个调用，原工作 MDB 哈希不变。
- 实际模型与新 MCP schema：完成读取解释，以及“复制为客户 CLF”的只读规划，返回 `inspect_designer_clf_plan` 通过，无工作 MDB 写入。
- 延迟查询回归：首次加载 CLF 后复用同一 SDK 图读取工作区目录，成功返回 25 个工作区，含 `200`；进程退出后常驻副本释放。
- 浏览器使用独立测试服务与隔离会话，验证详情、参数展开、解释请求、方案状态、刷新恢复及新建/切换对话。该测试服务不加载用户的实际会话。
- 自动化覆盖会话归属、模式过滤、旧会话兼容、越界工具/文件拒绝、规则来源与幂等带入、实际调用身份/顺序、预检前后值、测试状态、工具回执恢复和常驻副本寿命。
- 项目自动化回归：`python -m pytest tests -q`，555 项通过、57 项按环境条件跳过。

没有重启用户正在运行的 8032 服务。使用新入口前，需在适当时机重启服务加载后端代码。
