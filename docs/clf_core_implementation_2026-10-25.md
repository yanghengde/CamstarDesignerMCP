# CLF 核心工作区实施记录（2026-10-25）

> 本文保留首批交付时点的记录。后续同页验证、工作 MDB 保存/编译/恢复的当前进展见 [第二批实施记录](clf_core_phase2_2026-10-25.md)。

本轮实现了核心工作区、只读业务检查和测试/方案衔接。它是设计方案的分阶段交付，不代表 G0—G5 全部完成；厂商运行时能力、现场试用和交付链的门槛继续保留。

设计依据：[产品设计](clf_core_product_design.md)、[实施与验收合同](clf_core_delivery_and_acceptance.md)。

## 入口与使用

- `/clf`：新工作区；可切换业务检查、工程排查。
- 工程排查包含查看逻辑、验证与排查、修改方案；支持项目、规则、运行深链。
- `/clf?session_id=...`、`/clf/records`：原 CLF 对话及历史保持可用；`/clf?assistant=1` 保留原助手入口。
- `/clf-test`：复用既有真实测试工作台，工作区传入项目、规则、明确入口及连接选择；复制用例通过 `case_id` 载入。提供返回工作区链接。
- 服务已在 8032 重载。重载前检查没有运行中的聊天、测试及设计进度任务。

首次使用业务检查时，由工程师配置业务名称、项目、环境、客户端、真实服务方法及目标 CLF。没有配置或记录时显示真实空状态；本轮没有向用户正式数据植入演示映射或演示回执。

## 本轮实现

| 内容 | 实际行为与范围 |
|---|---|
| 独立上下文 | 使用现有测试 SQLite 中新增的 `clf_workspace_items` 表，按用户、类型、身份隔离，带 schema_version 和乐观修订；不改变已有回执表。浏览不创建聊天，刷新恢复项目、规则、模式、页签、同源函数和绑定选择 |
| 业务映射 | 保存前核对源哈希、环境修订、客户端哈希、真实服务方法和目标定义；草稿/启用查看/停用，来源变化衍生为待核对。签名核对与实际触发关系明确分开 |
| 只读检查 | 首期只检索当前用户、本项目的 CLF 测试回执，支持映射筛选、关键词和分页。完整回执按选择读取，不在首页加载所有报文 |
| 规则查看 | 复用真实目录和 CLF 查询；保留重复调用、调用 ID、原始表达式、声明及引用范围。目录按需加载和限制呈现高度 |
| 附着参数 | 使用官方 `CLFEventMap.AllFunctionParameters`，保留事件映射和参数身份、工作区及原始值；不回填库默认值冒充入口值 |
| 参数类型 | 从官方 FunctionDefinition/FunctionParameter 读取方向、类型、多重性和说明；缺失时显示未取得 |
| 四层呈现 | 库表达式、入口附着配置、业务输入、运行值分别显示。目前没有可靠的输入字段到函数参数映射和运行值证据时，明确标记缺项 |
| 分层结果 | 请求阶段、业务返回、断言、规则名称证据、版本关系分别展示；截断为部分未评估，未知结果不算成功，执行前阻止不写成已调用 |
| 后台任务阶段 | 现有执行器报告等待、前置校验、实际调用、独立回读及终态；界面不按计时猜测执行阶段。原幂等和后台恢复机制保留 |
| 历史复现 | 复制真实历史为草稿，原请求/回执不变，原版本固定，清除写入授权。修复旧 `loadCase` 在恢复参数后再次自动推荐入口、覆盖方法与输入的问题 |
| 用例组织 | 正常/异常/边界/自定义分组；保存后续版本保留 parent_run_id/parent_case_id 与修订。仍被后续修订引用的用例不能直接删除 |
| 运行对比 | 对同一项目的两次运行比较目标、入口、输入、环境、版本、预期及结果；差异不能直接归因于规则改动 |
| 方案预检 | 从当前参数构建原值/新值操作，或使用严格的十种 CLF 操作模型；直接调用现有官方内存预检，持久化项目方案回执，不开放保存/发布按钮 |
| 草稿来源 | 方案草稿保留源哈希；源改变后需明确核对并采用当前来源，不能自动沿用旧预检结果 |
| 上下文助手 | 实际提问才建立只读 CLF 对话；带入当前源、选中调用/绑定及相符运行证据。支持安全的基础 Markdown 呈现和完整对话回执链接 |
| 兼容与操作质量 | 旧对话、测试路由和一般 Designer 流程保留；统一 CLF 工作区菜单名称；键盘页签切换、窄屏重排、长表达式换行和明确时间区（UTC+08:00） |

附着参数和函数类型仅在工作区明确请求时展开；普通 MCP/助手的轻量 CLF 读取仍不附带全部入口参数，避免破坏此前的延迟优化。

## 数据与接口

新增主要模块：

- `designer/clf_workspace.py`：上下文、映射、只读检查、复制与对比。
- `web/clf_core_routes.py`：`/api/clf/workspace/*`，通过现有本机归属校验，不要求创建会话。
- `static/clf-core.html`、`.js`、`.css`：正式工作区。
- `tests/test_clf_core.py`：核心合同回归。

主要接口：bootstrap、context、project、rules、definition、operations、records、records/{id}/copy、records/{id}/export、compare、plans、assistant。模型禁止未知字段；业务执行仍只走 `/api/testing/runs` 等原执行边界。

映射的 `active` 仅表示可用于组织历史查看，不是已确认整条运行链。计划的 `metadata_preflight_passed`、原运行的 `runtime_verified`、客户端哈希也不会被解释为部署来源已经一致。

## 验证证据

1. 本机真实 Siemens SDK：读取 `ES_ValidateProduct` 的 7 个调用、1 个事件映射、9 项附着参数以及 4 个直接函数的参数定义；Condition 的官方方向为 In、类型为 Boolean。读取前后原工作 MDB 哈希一致。
2. 本机真实生成客户端：读取 795 个服务和实际方法；浏览器映射编辑只读取契约，不提交业务请求。
3. 隔离浏览器环境：使用真实 SDK/客户端契约及明确标识的隔离回执，验证映射保存、业务拒绝与断言分开、缺少规则证据、复制用例、输入/方法保留、写入授权清除、原版本固定及返回工作区。
4. 官方只读预检：在隔离验收环境准备 `ES_ValidateProduct` 的客户副本方案；内存预检通过，回执明确未保存、未绑定、未发布，原工作源不变。
5. 正式服务：验证入口、原对话兼容、真实绑定/参数类型；实际发送一次只读参数解释，助手成功使用当前函数与绑定证据。未向实际业务环境提交交易测试或写入。
6. 窄屏：352 像素视口下文档可用宽度 337，scrollWidth 同为 337，无横向溢出；长表达式可换行。桌面、模式切换和刷新恢复另作实际浏览器检查。
7. 自动化全量回归：648 项通过、57 项按环境条件跳过；新核心合同、原 CLF、原测试工作台均覆盖。最新上下文字段另经相关回归检查。

隔离浏览器记录位于 `tmp/clf-core-acceptance`；不是正式业务记录。测试用辅助服务在验收后停止，不改变现有 8032 服务的数据来源。
